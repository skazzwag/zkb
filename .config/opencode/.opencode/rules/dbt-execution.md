# Approved development dbt execution
Only analytics-engineer and reviewer can request python tools/dbt/run.py. No direct dbt, uv dbt, Python API, dbt MCP, altimate-dbt or Dagster bypass. No run-operation/full-refresh/arbitrary passthrough flags.
The runner is disabled until the user configures DBT_AGENT_CONFIG and verifies a separate development identity and production credential removal. Read docs/setup-dbt-safety.md. A boolean acknowledgement is not evidence that server permissions are safe; the user/admin verifies them.
Keep prod service credentials only in protected CI. Restart OpenCode and any persistent server after removing inherited credentials. Do not expose prod through cached auth, files, browser login, secret managers, Docker/WSL mounts or another MCP identity. Agent credentials can write only their own dev database and read approved production shares. A new token of the prod account is NOT a dev identity.
The runner generates a single agent_dev profile, maps only an explicitly supplied dev token, uses a separate HOME, target/log folders and schema per actor/session, validates non-prod identifiers and accepts a fixed command set. It does not sandbox arbitrary project code, override macros or enforce database permissions. It may be blocked by project-specific vars/adapter features; never bypass it. Review such changes with the user.
Use bounded selectors and the same session for build/docs/compile. Source changes require a new evidence session. A different reviewer schema requires a compatible generate_schema_name implementation and enough selected upstream models. Verify compiled effective destinations, especially access/mart models with explicit database settings. Never grant prod rights to make those models pass.
